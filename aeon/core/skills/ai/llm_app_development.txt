# AI SKILL: Building applications on top of LLM APIs
# Use when the task is to BUILD something that calls a language model — a chatbot,
# assistant, extraction/summarization/classification service, or a tool-using agent —
# rather than to train a model (see machine_learning/) or research a topic (see research/).
# Goal: a reliable, cost-aware LLM app whose outputs are validated, not vibes-checked.

1. MODEL & API SHAPE:
- Use the latest capable model for the job; a smaller/cheaper one for high-volume simple calls. It's a chat/messages API: a `system` message (role, rules, format) then alternating `user`/`assistant` turns. Roles MUST alternate — two user messages in a row is an error on many servers.
- Set `max_tokens` (the OUTPUT budget; it truncates silently — check `finish_reason=="length"` and retry shorter), and `temperature` (≈0 for extraction/classification/deterministic; 0.7+ for creative). temperature 0 is low-variance, NOT perfectly deterministic.
- The context window counts INPUT + OUTPUT together. Budget for both.

2. RELIABLE STRUCTURED OUTPUT (the #1 reliability lever):
- If the server supports it, CONSTRAIN generation to a JSON Schema (OpenAI "response_format: json_schema", vLLM guided_json/xgrammar, or tool/function calling). Grammar-constrained decoding makes malformed JSON and invalid enums IMPOSSIBLE — far better than asking "return JSON" and hoping. (This harness itself does exactly this.)
- If constraining is unavailable: request JSON, then parse DEFENSIVELY — strip ```fences```, extract the first balanced {...} object, tolerate trailing commas — and retry on failure. Never assume the raw text is valid JSON. Note: a plain "JSON mode" guarantees valid JSON but NOT your schema; validate the fields.

3. TOOL / FUNCTION CALLING (for agents):
- Define each tool with a clear name, description, and JSON-schema parameters. Run the loop: model emits a tool call -> you execute it -> feed the result back as a tool/user message -> repeat until the model returns a final answer. CAP the iterations (avoid infinite loops) and VALIDATE arguments before executing.

4. STREAMING & LATENCY:
- Stream tokens for responsive UX and to measure TTFT (time-to-first-token) vs generation speed separately.
- Prompt caching is the biggest latency win: keep the STATIC prefix (system prompt, tool defs, few-shot) BYTE-IDENTICAL across calls so the server reuses its KV cache; put the volatile/user content LAST.

5. COST, CONTEXT & MEMORY:
- Count tokens; log input/output tokens per call. For chat history, trim or summarize old turns before they blow the window. Retrieval (see ai/rag_pipeline) beats stuffing everything in the prompt.

6. ROBUSTNESS:
- Wrap calls with timeouts and retries-with-backoff; handle rate-limit (429) explicitly. Treat any user/web/tool text inserted into the prompt as UNTRUSTED — delimit it and instruct the model to treat it as data, not instructions (prompt-injection defense).

7. EVALUATE (do NOT ship on vibes):
- Build a small eval set (representative inputs -> expected outputs / a rubric). Score every prompt or model change against it. Track accuracy/format-validity/cost. One-off "looks good" testing hides regressions.

COMMON MISTAKES:
- Assuming the raw response is valid JSON (constrain or parse defensively). "JSON mode" != schema-valid.
- Ignoring finish_reason=="length" (silently truncated output).
- Non-alternating roles; forgetting the context window includes the output.
- Busting prompt caching by putting volatile content early or changing the system prompt each call.
- Embedding untrusted text without injection defense.
- No eval set -> silent quality regressions on every prompt tweak.
