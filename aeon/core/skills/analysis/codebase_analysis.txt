# CODEBASE SKILL: Evidence-led analysis of an existing repository
# Use when understanding or auditing an unfamiliar codebase requires tracing architecture and behavior across files or boundaries.

## When to use

Use for architecture mapping, correctness or risk audits, and substantial reviews of
an existing repository. Skip it for a simple lookup or a well-understood isolated
edit that does not need broader dependency tracing.

## Preconditions

- Establish the requested outcome and whether the task is read-only.
- Read applicable workspace instructions and inspect the current tree, entry points,
  build/configuration files, and relevant dirty-worktree state.
- Separate confirmed source behavior from documentation, history, and hypotheses.

## Procedure

1. Identify the smallest architectural spine that explains the request: entry
   points, core modules, persisted state, and process or external-system boundaries.
2. Trace representative control and data flows end to end. For important contracts,
   inspect both callers and consumers rather than summarizing files independently.
3. Evaluate the risks relevant to the request, such as incorrect assumptions,
   broken interfaces, silent failures, races, resource leaks, or authority gaps.
4. Use outside research only when domain knowledge is necessary, favoring current
   primary sources. Use read-only sub-agents only for genuinely independent areas
   where parallel work outweighs handoff cost, and verify consequential reports.
5. Synthesize around the user's question: architecture, concrete findings ordered
   by impact, supported recommendations, and remaining uncertainty.

## Verification

- Support code claims with exact current files, symbols, or observed behavior.
- Recheck important dependency and call-flow claims with repository search.
- Label findings as confirmed, likely, or uncertain; never turn a small sample or
  missing search result into proof of system-wide absence.

## Stop or adapt

If evidence disproves the initial architecture map, revise the map before proceeding.
If the task changes from analysis to implementation, reassess scope and authority
instead of treating this playbook as permission to edit. Stop once the requested
question is supported; do not inspect unrelated subsystems for completeness theater.
