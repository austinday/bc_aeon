# DISTRIBUTED SKILL: Find, access & inventory other computers on the LAN.
# Use FIRST for "use the other machines / all the computers on the network", or when
# given remote hosts or credentials. Sets up SSH + a verified GPU/CPU inventory.

## OBJECTIVE
Turn "use the other computers" into a CONCRETE, VERIFIED inventory: a list of hosts you can actually reach non-interactively, each with known GPUs, CPUs, RAM, disk, interconnect, and Python/CUDA environment. Never guess any of this — every field is a command away, and a wrong guess silently wastes the whole run.

## 0. SCOPE & AUTHORIZATION (do this before touching the network)
- Only ever scan/access networks and hosts the user has authorized. If scope is unstated, ASK with `get_user_input` — do not sweep an unknown subnet on your own initiative. "Use all available computers" authorizes the user's OWN machines, not everything that answers a ping.
- Ask once, ask for everything: host list (or subnet), username, auth method (key path or password), and any host that is off-limits. One `get_user_input` with a clear list beats five round-trips.
- PREFER A USER-SUPPLIED HOST LIST over discovery. It is faster, unambiguous, and cannot stray. Discover only when the user genuinely doesn't know what's out there.

## 1. DISCOVERY (only if you have no host list)
- Find your own subnet first: `ip -4 addr show` (the /24 or /16 on the LAN interface) or `ip route get 1.1.1.1` (shows the interface + source IP actually used).
- Sweep: `nmap -sn 192.168.1.0/24` (ping sweep, no port scan). Then find who takes SSH: `nmap -p22 --open 192.168.1.0/24`.
- No nmap? Fallbacks: `ip neigh` / `arp -a` (hosts already talked to), `avahi-browse -art` or ping `<name>.local` (mDNS names on most Linux/macOS LANs).
- A host that answers a ping is NOT a usable host. It is a candidate. Nothing counts until step 3 verifies it.

## 2. ESTABLISH NON-INTERACTIVE SSH (the part that actually breaks)
- Key-based auth is the goal. Generate a dedicated key (never reuse a user key silently):
  `ssh-keygen -t ed25519 -N '' -f ~/.ssh/aeon_cluster -C aeon-cluster`
  then install it: `ssh-copy-id -i ~/.ssh/aeon_cluster.pub user@host` (this is the ONE step that may need the password).
- If given a password and `ssh-copy-id` isn't viable, `sshpass -p "$PW" ssh ...` works but is a STOPGAP — install the key on the first successful connection and stop using the password.
- **THE #1 FAILURE: an SSH that prompts is an SSH that HANGS**, silently burning your entire `run_command` timeout on an invisible "Are you sure you want to continue connecting?" or password prompt. Every non-interactive SSH MUST carry:
  `ssh -o BatchMode=yes -o ConnectTimeout=5 -o StrictHostKeyChecking=accept-new -o PasswordAuthentication=no`
  `BatchMode=yes` turns a prompt into an instant, readable FAILURE instead of a hang. Use it always. (`accept-new` trusts a first-seen host key but still errors on a CHANGED one; on an untrusted network, verify fingerprints out-of-band instead.)
- Write `~/.ssh/config` once so every later command is short and consistent, and multiplex connections (a 10x speedup on fan-out — one TCP+auth handshake, reused):
  ```
  Host gpu1
      HostName 192.168.1.21
      User aday
      IdentityFile ~/.ssh/aeon_cluster
      BatchMode yes
      ConnectTimeout 5
      StrictHostKeyChecking accept-new
  Host *
      ControlMaster auto
      ControlPath ~/.ssh/cm-%r@%h:%p
      ControlPersist 10m
      ServerAliveInterval 30
  ```
  After this, `ssh gpu1 'hostname'` is a safe reachability check. `ControlPersist` keeps the tunnel warm between your commands.
- Never put a password in a command line you log (it lands in your transcript, the host's history, and `ps`). Read it via `get_user_input`, use it once to install the key, and never again.

## 3. INVENTORY EACH HOST — VERIFY, DON'T ASSUME
Run one compact probe per host and record the answers. Hosts on the same LAN are routinely NOT identical:
- GPUs and occupancy: on this managed fleet, run `python3 ../gpu_coord.py status`
  only from `/home/aday/website_hosting/ads` on `.177`. It combines physical
  device ACLs, stable UUID identity, leases, and process evidence. Never use
  `nvidia-smi` to enumerate capacity because renter-blocked devices disappear or
  renumber. Treat rented, ambiguous, unexplained, or unclaimed states as unavailable.
- A single GPU can host more than one process only when each process has its own
  coordinator claim, UUID selector, truthful hard VRAM cap, and the combined
  budgets plus at least 6 GB fit. Never kill or inspect a process you do not own.
- CPU/RAM/disk: `nproc`, `free -g`, `df -h /` and the intended work dir.
- Environment: `python3 -VV`, `which python3`, and the installed framework/CUDA
  package versions. Do not interpret framework-visible device counts as physical
  fleet inventory.
- Interconnect (decides whether multi-node training is even worth it): `ip -br link` for link speed; measure real bandwidth with `iperf3 -s` on one host and `iperf3 -c <host>` on another. 1 GbE ≈ ~940 Mb/s ≈ 118 MB/s — record the number, `distributed/distributed_training` depends on it.
- Shared storage: does an NFS/SMB mount exist on all hosts (`mount | grep -E 'nfs|cifs'`)? Shared FS vs per-host disk changes every later data decision.

## 4. PERSIST THE INVENTORY
- Write it to a machine-readable file, e.g. `aeon_output/cluster/inventory.json`, one record per host: alias, address, user, reachable(bool), gpus[{index,name,total_gib,free_gib}], cpus, ram_gib, torch/cuda versions, iperf3 Mb/s, shared mounts, notes.
- `memorize` the durable, non-obvious facts (host aliases, which have GPUs, key path, interconnect speed) so a later session doesn't re-derive the whole cluster.
- Re-verify reachability and free VRAM at the START of each new run. Inventories go stale: laptops sleep, someone else claims a GPU, hosts reboot.

## 5. REPORT & PROCEED
- Tell the user plainly what you found: N hosts reachable, M with GPUs, total usable VRAM, interconnect speed, and any host you could NOT reach and why. If a host fails auth, say so — do not quietly drop it and pretend the cluster is smaller.
- Then choose the execution shape: independent work → `distributed/parallel_workload_distribution`. One model, one collective run → `distributed/distributed_training`. Either way, operate hosts via `distributed/remote_execution_and_monitoring`.

## COMMON MISTAKES
- SSH without `BatchMode=yes`/`ConnectTimeout` → a hang that looks like a slow network but is a hidden prompt.
- Treating "it pings" or "the user said there are 4 machines" as an inventory. Probe it.
- Assuming all hosts have the same GPUs, CUDA, paths, or usernames. They don't.
- Counting TOTAL VRAM as FREE VRAM while another user's job is resident.
- Scanning beyond the authorized scope; leaving a password in a logged command line.
