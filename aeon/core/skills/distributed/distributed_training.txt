# DISTRIBUTED SKILL: Multi-node training — torchrun, NCCL, DDP/FSDP.
# Use ONLY when ONE training run must span GPUs on MORE THAN ONE computer.
# Single-machine/multi-GPU -> machine_learning/deep_learning_training.

## OBJECTIVE
A multi-node run that actually converges and is actually FASTER than one node — verified by a smoke test before you commit hours of GPU time.

## 1. FIRST, DECIDE IF MULTI-NODE IS EVEN WORTH IT (do not skip this)
Multi-node is not free speed. Every DDP step all-reduces the FULL gradient across the network, so the interconnect, not the GPUs, often sets the pace.
- Rule of thumb: all-reduce moves ~2×(model params × bytes/param) per step per node. A 1B-param bf16 model ≈ 2 GB of gradients ≈ **~17 seconds** to shift over 1 GbE (~118 MB/s), against a step that computes in well under a second. On 1 GbE, 2 nodes are routinely SLOWER than 1. This is the single most common multi-node mistake.
- So: use the `iperf3` number from `distributed/cluster_discovery_and_access`. 1 GbE → do NOT multi-node a big model; instead use one node with a larger batch / gradient accumulation, or shard the WORK (`distributed/parallel_workload_distribution` — a hyperparameter sweep parallelizes perfectly over slow links; a single DDP run does not). 10 GbE → viable for modest models. InfiniBand/RDMA or 100 GbE → multi-node as intended.
- Legitimate reason to multi-node on a slow link: the model does NOT FIT on one node. Then you need FSDP/DeepSpeed sharding and you accept the network cost because there's no alternative.
- Say this tradeoff OUT LOUD to the user before burning the cluster. "4 machines" sounds like 4x and usually isn't.

## 2. PRECONDITIONS — IDENTICAL, VERIFIED, ON EVERY NODE
Version skew across nodes surfaces as a HANG at init, not a clean error. Verify, don't assume:
- Same torch + CUDA + NCCL build on all nodes: `ssh $h '/opt/venv/bin/python -c "import torch;print(torch.__version__, torch.version.cuda, torch.cuda.nccl.version())"'`.
- Same code, same commit — `rsync` it, don't hand-copy. Same data at the same absolute path (shared FS, or replicated to local disk on each node).
- GPU count per node known. HETEROGENEOUS GPUs: the SLOWEST GPU sets every step's pace (all ranks sync each step), and the batch must fit the SMALLEST VRAM. Prefer a homogeneous subset over "use everything" — 4 matched GPUs usually beat 6 mismatched ones.
- Firewall open between nodes on the rendezvous port (e.g. 29500) and the ephemeral range NCCL uses. A "hang at init" is frequently just a blocked port.

## 3. LAUNCH — torchrun ON EVERY NODE
`python -m torch.distributed.launch` is DEPRECATED — use `torchrun`. Launch it on EACH node (one command per node, in parallel via your async jobs; `torchrun` is not a scheduler and does not reach out to other machines for you).
- Modern c10d rendezvous (preferred — same command everywhere except `--node-rank`, and no static master):
  ```
  torchrun --nnodes=2 --nproc-per-node=2 --node-rank=0 \
           --rdzv-id=aeon_run1 --rdzv-backend=c10d --rdzv-endpoint=192.168.1.21:29500 \
           train.py
  ```
  `--rdzv-endpoint` is HOST:PORT of ONE chosen node (node 0). It must be an address the other nodes can actually reach — NOT `localhost`, NOT `127.0.0.1`. Every node needs the SAME `--rdzv-id`.
- `--nproc-per-node` = GPUs on THAT node. `--node-rank` is unique per node (0..N-1); node 0 hosts the rendezvous.
- In the script, read the device from the env var `LOCAL_RANK` (torchrun sets `LOCAL_RANK`, `RANK`, `WORLD_SIZE`). The old `--use_env` flag is gone.
  ```python
  import os, torch, torch.distributed as dist
  local_rank = int(os.environ["LOCAL_RANK"])
  torch.cuda.set_device(local_rank)          # BEFORE init_process_group
  dist.init_process_group(backend="nccl")
  model = torch.nn.parallel.DistributedDataParallel(model.to(local_rank), device_ids=[local_rank])
  ```
- Each node's torchrun is a long job → launch DETACHED with logs per node (see `distributed/remote_execution_and_monitoring`). Never foreground it.

## 4. NCCL CONFIG — WHERE THE HANGS LIVE
A multi-node job that prints nothing and never starts is almost always NCCL picking the wrong network interface.
- `NCCL_SOCKET_IFNAME=eth0` — **set it explicitly whenever a host has multiple NICs** (docker0, virbr0, wlan0, tailscale, br-*). NCCL will otherwise try a bridge that routes nowhere and hang forever. Get the real interface from `ip -br addr` (the one carrying the LAN IP). `GLOO_SOCKET_IFNAME` likewise if you use the gloo backend.
- `NCCL_IB_DISABLE=1` if there is no InfiniBand (plain ethernet clusters).
- `NCCL_DEBUG=INFO` on the first run — it prints the interface and transport it selected. Read it; it tells you directly what went wrong.
- `nccl` is the backend for GPU collectives; `gloo` is for CPU. Don't use gloo for GPU training.
- Diagnosis: hang at `init_process_group` → interface/firewall/rendezvous unreachable. Hang mid-training → one rank died (read EVERY node's log, not just rank 0) or ranks disagree on a collective. Every rank must execute the SAME collectives in the SAME order — a conditional `if rank == 0: dist.all_reduce(...)` deadlocks the job.

## 5. SMOKE TEST BEFORE THE REAL RUN (non-negotiable)
Never debug a distributed setup through a real training script. Run a ~10-line, 1-step job across all nodes first:
```python
import os, torch, torch.distributed as dist
dist.init_process_group(backend="nccl")
torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))
t = torch.ones(1, device="cuda") * dist.get_rank()
dist.all_reduce(t)
print(f"rank {dist.get_rank()}/{dist.get_world_size()} -> {t.item()}")
dist.destroy_process_group()
```
Expected sum for world size N = 0+1+...+(N-1). Correct number = rendezvous, interconnect, NCCL, and topology all verified in ~30 seconds. Wrong/hanging = fix THIS, where the surface is 10 lines, not 500.

## 6. DATA, CHECKPOINTS, AND CORRECTNESS
- Use `DistributedSampler` so each rank sees a DIFFERENT shard, and call `sampler.set_epoch(epoch)` EVERY epoch — forget it and every epoch reshuffles identically, quietly hurting convergence.
- Effective batch = per_device_batch × nproc_per_node × nnodes × grad_accum. Scaling nodes scales the effective batch, so the LR usually needs rescaling (linear-scaling with warmup is the standard starting point). Multi-node with an unchanged LR often just trains worse — this is a correctness bug that shows up only as a mediocre metric.
- Checkpoint from RANK 0 ONLY (`if dist.get_rank() == 0: torch.save(model.module.state_dict(), ...)`) — note `.module` to unwrap DDP — to shared storage or a path you rsync back. Every rank writing the same file corrupts it.
- Multi-node runs DIE (a node reboots, someone else grabs a GPU, the network blips). Checkpoint frequently and make resume work. An 8-hour run with no resume is an 8-hour run you will do twice.
- Log from rank 0 only, or you get W duplicate lines of everything.

## 7. WHEN DDP ISN'T THE RIGHT TOOL
- Model doesn't fit on one GPU → FSDP (`torch.distributed.fsdp`) or DeepSpeed ZeRO-3 shards params/grads/optimizer state. More network traffic than DDP — the step-1 interconnect math matters even more.
- Independent runs (hyperparameter sweep, many models, batch inference) → NOT this skill. `distributed/parallel_workload_distribution`; it needs no NCCL, tolerates slow links, and scales far better.
- Complex orchestration/elasticity → Ray or a real scheduler (Slurm), rather than hand-rolling.

## COMMON MISTAKES
- Multi-node over 1 GbE for a run that fits on one node — slower than one machine, and nobody checks.
- `NCCL_SOCKET_IFNAME` unset on a multi-NIC/docker host → silent forever-hang at init.
- `--rdzv-endpoint` set to localhost, or a different `--rdzv-id`/`--node-rank` per node than intended.
- Version skew across nodes; assuming venv is active over SSH (it isn't).
- Forgetting `sampler.set_epoch()`; not rescaling LR for the larger effective batch.
- Saving checkpoints from all ranks; reading only rank 0's log when a different rank is what died.
- Debugging the setup through the real training script instead of a 10-line all-reduce.
