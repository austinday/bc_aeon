# Verifying Change Propagation Protocol

This skill is to be implemented whenever the agent intends to make a change to an existing codebase to standardize the analysis of implications and ensure system stability.

## Phase 1: Dependency Mapping
1. **Initial Analysis:** Identify the target file(s) for modification.
2. **Link Identification:** Identify all other files that call the target file (upstream) and all files that the target file calls (downstream).
3. **Sub-Agent Deployment:** For each identified link (upstream or downstream), spawn a dedicated sub-agent to analyze the specific connection.
4. **Analysis Criteria:** Each sub-agent must evaluate:
    - **Path Dependencies:** Are file paths still valid? Are files expected to be in locations that have changed?
    - **Interface Integrity:** Are function signatures, class interfaces, or API contracts still valid? (e.g., check for new flags, changed arguments, or removed optional parameters).
    - **Connectivity:** Are there any broken imports or calls resulting from the change?
    - **Renaming Awareness:** If the target file was renamed, the sub-agent must compare the previous filename/structure with the new one to ensure all references are updated.
    - **Constraint:** Sub-agents are strictly forbidden from making changes; they perform search and analysis only.

## Phase 2: Consensus Audit
1. **Synthesis:** The primary agent collects all reports from the dependency sub-agents.
2. **Audit Spawning:** The primary agent must spawn at least 3 independent audit sub-agents.
3. **Audit Task:** Each auditor is provided with the proposed changes and the dependency reports. They must independently audit the potential implications and determine if the changes are safe or likely to cause regressions.
4. **Consensus Evaluation:** The primary agent assesses the 3 audit reports:
    - **Positive Consensus:** If at least 2 out of 3 auditors agree the changes are safe, the primary agent may proceed.
    - **Negative Consensus:** If at least 2 out of 3 auditors identify a specific issue, this is treated as a confirmed bug/regression.

## Phase 3: Iterative Correction
1. **Debugging:** If a negative consensus is reached, the primary agent uses the audit findings as debugging input to correct the proposed changes.
2. **Verification Loop:** After correcting the changes, the agent must repeat Phase 1 and Phase 2 from the beginning to ensure the new fix hasn't introduced further propagation issues.
3. **Final Implementation:** Only the primary agent is authorized to write changes to the codebase. All other agents remain in an advisory/validation role.
