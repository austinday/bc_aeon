# CODING SKILL: Evidence-led root-cause debugging
# Use when a reproducible or observable failure must be explained and fixed without looping on guesses.

## When to use

Use for crashes, failing tests, installation or import failures, incorrect output,
API failures, and data or numerical errors. Skip it for general code review when no
specific failure or violated expectation exists.

## Preconditions

- Record the expected behavior, actual behavior, exact error or strongest available
  evidence, and the environment in which it occurred.
- Inspect applicable instructions and current workspace state before changing it.
- Confirm that the request authorizes a fix; diagnosis alone remains read-only.

## Procedure

1. Reproduce the smallest useful failure when practical. If it is intermittent or
   cannot be safely reproduced, preserve logs, inputs, traces, and timing evidence
   rather than declaring it unfixable.
2. Locate the first point where observed state diverges from expected state. Form
   only the few hypotheses supported by that evidence, then choose the cheapest
   probe that distinguishes among them.
3. Check the relevant boundary before editing:
   - Environment/dependency: executable and interpreter, import path, installed and
     expected versions, resolver or compiler error, and runtime/build mismatch.
   - HTTP/API: status, response body, headers and content type; distinguish request,
     authentication, rate-limit, server, transport, TLS, and browser-CORS failures.
   - Data/numerical: shapes, dtypes, ranges, missing/non-finite values, counts before
     and after transforms, index or join cardinality, and the first corrupt record.
4. Apply the smallest change that addresses the demonstrated mechanism. Inspect
   direct callers and consumers when the changed contract could propagate.
5. Re-run the original reproduction or strongest equivalent check, then run nearby
   regression tests in proportion to the change.

## Verification

- Show that the original symptom is gone under the same relevant conditions.
- Verify the causal mechanism, not merely a different exit code or hidden symptom.
- Inspect fresh output and record any nondeterminism or environment not exercised.

## Stop or adapt

Do not repeat a failed probe or fix unless a named precondition changed. When evidence
contradicts the current hypothesis or this playbook's assumptions, discard that path,
deactivate or adapt the skill, and choose a materially different diagnostic. Report a
truthful blocker when the necessary evidence or authorization is unavailable.
