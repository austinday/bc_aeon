# DEEP LEARNING SKILL: Neural Network Training & Debugging Protocol
# Triggered when building or training neural networks (PyTorch/TF/JAX) or debugging
# training dynamics. Goal: a correctly-learning model with verified training behavior.

1. PIPELINE SANITY BEFORE SCALE:
- Verify the data pipeline end-to-end: shapes, dtypes, value ranges, label correctness, and that augmentation is applied to TRAIN only.
- OVERFIT A TINY BATCH first: a correct model+loss must drive loss toward ~0 on a handful of examples. If it cannot, the model/loss/data wiring is broken — fix that before any real training.

2. ENVIRONMENT & RESOURCES:
- Containerize with pinned framework + CUDA versions matched to the hardware. Check GPU availability and free VRAM before allocating; size batch/precision to fit.
- Use mixed precision and the largest stable batch size for throughput; enable checkpointing for long runs.

3. TRAIN WITH INSTRUMENTATION:
- Fix seeds. Log train AND validation loss/metrics every epoch (or step). Watch for divergence, NaNs, and the train/val gap.
- Start from sane defaults for LR/optimizer/schedule; use an LR warmup/schedule. Tune LR first — it dominates.

4. DIAGNOSE TRAINING FAILURES:
- Loss NaN/exploding -> lower LR, add grad clipping, check for bad inputs / log of zero.
- Not learning (flat loss) -> check LR too low, frozen params, broken gradient flow, or mislabeled data.
- Train good / val bad (overfitting) -> add regularization/augmentation/early stopping or more data.
- Both poor (underfitting) -> more capacity, longer training, or better features.

5. EVALUATE & VALIDATE:
- Evaluate on a held-out test set ONCE. Report variance across seeds where feasible.
- Confirm no data leakage between splits (apply the ml_experiment leakage checks).

6. DOCUMENT:
- Save a README with architecture, data version, seeds, hyperparameters, the tiny-batch overfit check result, and final metrics.

7. COMMON FLAG/API MISTAKES — GET THESE RIGHT THE FIRST TIME (older training docs are frequently WRONG here; trust this over your priors):
- PyTorch Lightning device selection: `Trainer(gpus=N)` was DEPRECATED in 1.7 and REMOVED in 2.0. The correct current form is `Trainer(accelerator="gpu", devices=N)` — `devices="auto"` = all GPUs, `devices=[0,1]` = specific ones. For multi-GPU add `strategy="ddp"`. The old `distributed_backend=` / `accelerator="ddp"` are gone. LightningCLI flags are `--trainer.accelerator gpu --trainer.devices N` (NOT `--gpus`). This is the single most-common wrong flag.
- Lightning precision is STRING-valued now: `precision="bf16-mixed"` / `"16-mixed"` / `"32-true"`. The bare int `precision=16` is legacy.
- Distributed launch: `python -m torch.distributed.launch` is DEPRECATED → use `torchrun --standalone --nproc_per_node=N script.py`. Read the device from the env var `LOCAL_RANK` (torchrun sets it; the old `--use_env` is no longer needed).
- GPU selection at the PROCESS level is `CUDA_VISIBLE_DEVICES=0,1 python ...` (0-indexed physical GPUs). Inside the process those remap to cuda:0/cuda:1 — never confuse the physical index with the logical one.
- Mixed precision: on Ampere/Hopper/Blackwell (A100/H100/RTX 40–50/PRO 6000) prefer BF16 over FP16. BF16 needs NO gradient scaler and is far more numerically stable; FP16 REQUIRES `torch.cuda.amp.GradScaler` or it silently diverges. Autocast: `with torch.autocast("cuda", dtype=torch.bfloat16):` (the unified API; the old `torch.cuda.amp.autocast()` still works).
- HuggingFace TrainingArguments: effective batch = `per_device_train_batch_size` (NOT `batch_size`) × `gradient_accumulation_steps` × num_gpus. Use `bf16=True` (not `fp16`) on modern GPUs. The arg `evaluation_strategy` was renamed to `eval_strategy` in transformers 4.46 (older versions still expect `evaluation_strategy` — match the installed version). For `load_best_model_at_end=True`, `save_strategy` must equal `eval_strategy` and save/eval steps must align. Use `optim="adamw_torch"`.
- Optimizer: use `torch.optim.AdamW` (decoupled weight decay), NOT `Adam(..., weight_decay=)` (that is coupled L2 and behaves differently). Typical LR: from-scratch transformer 1e-4–3e-4 with warmup; fine-tuning a pretrained model 1e-5–5e-5. LR dominates — tune it first.
- Inference/validation: call `model.eval()` AND wrap in `torch.no_grad()` — forgetting `eval()` leaves dropout/BatchNorm in train mode and silently corrupts results. `optimizer.zero_grad()` before each `backward()`.
- Checkpoints: save `model.state_dict()`, not the pickled model object. torch 2.6+ defaults `torch.load(..., weights_only=True)`, so loading an older FULL checkpoint now needs `weights_only=False` (trusted files only) — or just save/load a state_dict.
- DataLoader throughput: set `num_workers>0`, `pin_memory=True`, `persistent_workers=True`. The default `num_workers=0` starves the GPU and is a common "why is my GPU at 10%" cause.

8. LLM FINE-TUNING SPECIFICS (when adapting a language model, not a generic net):
- Prefer QLoRA on limited VRAM: load the base in 4-bit via bitsandbytes `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype=torch.bfloat16)`, then call `peft.prepare_model_for_kbit_training(model)` BEFORE `get_peft_model(model, LoraConfig(...))`, and enable `gradient_checkpointing`. Order matters — kbit-prep after get_peft_model breaks it.
- LoRA `target_modules` must match the architecture's projection names (Llama/Qwen-style: q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj). `target_modules="all-linear"` is the safe modern default that avoids naming mistakes.
- ALWAYS format data with the model's OWN chat template (`tokenizer.apply_chat_template(...)`); a hand-written prompt format silently degrades an instruct model. If the tokenizer has no pad token, set `tokenizer.pad_token = tokenizer.eos_token`. For instruction tuning, mask the prompt tokens out of the loss (train on completions only).
- Merge for deployment (`model = model.merge_and_unload()`) and serve the merged weights, or keep the adapter and load it via the server's LoRA support (e.g. vLLM `--enable-lora`).
